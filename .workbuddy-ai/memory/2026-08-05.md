# 2026-08-05

## Video player — YouTube-style rewrite + hydration fix

User requested that the watch page video player (`app/[locale]/student/courses/watch/[chapterId]/`) match the YouTube-style player in a reference image (info icon top-right, bottom controls row, settings menu with Annotations / Sleep timer / Playback speed / Quality, theater mode, CC, fullscreen, prev/next chapter, red progress bar with red playhead dot). Page was blank because a pre-existing hydration mismatch in `StudentLayoutShell` tore down the tree on every navigation.

### Files touched
- `components/student/watch/HlsVideoCustomControls.tsx` — full rewrite of the control bar to match the image (circular buttons, red track, settings overlay panel, sleep timer countdown, prev/next chapter, CC, theater mode, info icon).
- `components/student/watch/HlsVideoPlayer.tsx` — pass-through of new props (`onPrevChapter`, `onNextChapter`, `canPrevChapter`, `canNextChapter`, `chapterInfoTitle`, `theaterMode`, `onToggleTheater`).
- `components/student/ChapterWatchView.tsx` — derive prev/next chapters from `partChapters` + `currentPartIndex`, wire callbacks to the player, persist theater mode in `localStorage` (key: `student.watch.theaterMode`), expand container width when theater is on.
- `components/student/StudentLayoutShell.tsx` — added `hasMounted` gate (with `useEffect` setting it after hydration) to keep SSR and first client render identical and stop Zustand `persist` from causing a hydration mismatch.
- `messages/en.json`, `messages/ar.json` — added keys for the new controls (`videoControlsSettings`, `videoControlsInfo`, `videoControlsPrevChapter`, `videoControlsNextChapter`, `videoControlsCaptions`, `videoControlsTheater`, `videoControlsAnnotations`, `videoControlsSleepTimer`, etc.).

### Key gotchas
- The hydration error trace pointed to `Sidebar.tsx:357` but the actual mismatch is much higher up: Zustand's auth store reads cookies via `getTokenFromCookies()` on the client synchronously, so server (no token) and client (token) diverge before `StudentLayoutShell`'s `useAuth()` runs. The `hasMounted` pattern (return spinner until `setHasMounted(true)` in a one-shot `useEffect`) is the cleanest fix without rewriting the auth store.
- `react-hooks/set-state-in-effect` flags the `setHasMounted(true)` call; suppress locally with `// eslint-disable-next-line` because the pattern is the documented way to opt out of server-side state knowledge.
- `HlsVideoCustomControls` is a client component but gets SSR'd; ensure all `useState` initial values are deterministic (no `window`/`localStorage`/`Date.now()` in initial state) and put any browser-only reads in `useEffect`.

## Chapter view-limit UX — don't pause the video

User reported that when the chapter view counter increments (POST `/v1/chapter/:id/view` succeeds for the last allowed view, or fails because the limit was already hit), the hook was calling `el.pause()` on the `<video>` and stopping playback mid-watch. They want the video to keep playing until it finishes naturally; only the next page entry should be blocked (which the existing server-side `can_watch` gate in `ChapterWatchView` already handles via `clientPlaybackBlocked`).

### Fix
- `src/hooks/useChapterViewRecording.ts` — removed the `el.pause()` call from the `recordViewOnce` catch block and switched `recordedRef.current = false` to `true` on failure (so we don't spam the API + toast on every `playing` event after a permanent failure). The toast still fires via the existing `onViewRecordError` callback wired in `ChapterWatchView`.

### Mental model
- View counting is best-effort and non-blocking from the player's perspective.
- Access enforcement lives on `can_watch` from the chapter payload (and the `coerceCanWatchExplicitTrue` helper), checked when the user *enters* the chapter. The recording hook should never abort active playback.
